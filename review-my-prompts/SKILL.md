# 自分のプロンプトを評価する

評価対象は**ユーザーが Claude に向けて書いた文**であって、Claude の出力ではない。
狙いは点数付けではなく、**次の指示を1回で通すこと**。

## 手順

1. プロンプトを抽出する（ツール結果やシステム注入を混ぜない）

   ```bash
   python ~/.codex/skills/review-my-prompts/scripts/extract_prompts.py <セッションID>
   python ~/.codex/skills/review-my-prompts/scripts/extract_prompts.py <セッションID> --last 15
   ```

   セッションIDはトランスクリプトのファイル名（拡張子なし）。
   Windows で文字化けするときは `PYTHONIOENCODING=utf-8` を付ける。

2. 各プロンプトを3軸で採点する（下の基準）

3. **そのプロンプトの直後に何が起きたか**を会話から確認する。
   ここが評価の核心。手戻り・聞き返し・別方向への着手が起きていれば、
   それは軸のどこが欠けた結果か言えるはず。**推測で減点しない**

4. 報告する（下の型）

## 3つの軸

### 1. 結論ベース — 何をしてほしいかが冒頭にあるか

| 点 | 状態 |
|---|---|
| 3 | 1文目で依頼が確定する。背景はその後 |
| 2 | 依頼はあるが、経緯や愚痴を挟んでから出てくる |
| 1 | 状況説明だけで、何をしてほしいのか本文から読み取れない |

例:
- 3点 —「役場職員の画面でログアウトができない」（症状＝直せ、が1文目で確定）
- 1点 —「なんか最近重い気がする」（報告なのか調査依頼なのか修正依頼なのか不明）

### 2. 簡潔 — 冗長さではなく、判断に不要な情報が無いか

短ければ良いのではない。**制約や前提は簡潔さより優先する**。
削るべきは「読んでも行動が変わらない情報」。

| 点 | 状態 |
|---|---|
| 3 | 判断に要る情報だけがある。制約は落ちていない |
| 2 | 要る情報はあるが、前置き・繰り返しがある |
| 1 | 長いのに肝心の制約が抜けている／短すぎて前提が足りない |

**1点の典型は「短くて曖昧」のほう**。長さより欠落を見る。

### 3. 目的が明確 — 何が達成されたら終わりか分かるか

| 点 | 状態 |
|---|---|
| 3 | 完了条件（動く状態・見た目・通るテスト）が読み取れる |
| 2 | 方向は分かるが、どこで止めるかは Claude の判断に委ねられている |
| 1 | 完了条件が無く、どこまでやるかが決められない |

「実機確認」のような一言でも、文脈上その対象が一意に決まるなら3点でよい。
**会話の文脈で埋まっている情報を、プロンプト単体で欠落扱いにしない。**

## 報告の型

まず全体の傾向を1〜2文。次に、**直したら一番効く1点**。最後に具体例。

> 直近15件の平均は 結論ベース 2.7 / 簡潔 2.4 / 目的 2.1。
> 一番効くのは**目的（完了条件）**。3件で「どこまでやるか」を書かなかった結果、
> 実装が広がって差し戻しになっている。
>
> **効いた例** — 「役場職員の画面でログアウトができない。役場管理者画面の設定で
> メインがスクロールしないから崩れている。こういう場合はスクロールさせて良い」
> → 症状・場所・許容する解法が揃っていて、聞き返しゼロで直っている。
>
> **効かなかった例** — 「隊員画面のPC版を作成」
> → 既存実装の有無を確認する往復が1回入った。「あれば直す、無ければ作る」を
> 書いておけば省けた。
>
> **次の1手**: 依頼の末尾に「〜が〜になっていれば完了」を1行足す。

## やらないこと

- **プロンプトの書き直し案を全件分並べない。** 直す価値のある2〜3件に絞る
- **短さそのものを減点しない。** 「実機確認。」で通っているなら3点
- 丁寧語の有無・語調・日本語の崩れを評価軸にしない。3軸だけを見る
- 会話の後半だけを見て「文脈が足りない」と言わない。前のターンで与えられていないか確認する
- 点数を出して終わりにしない。**次の1手を必ず1つ出す**
