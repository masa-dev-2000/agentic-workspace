# 協力隊サポート UI 規約

このプロダクトのUIを作るときの制約。**この1枚が正。**毎回書き下さず、これを参照する。
色・タイポの実値は `v2/docs/05_design_system.md`、画面の実体は `v2/docs/mock/member-mock-v56.html`。

## 1. 出すな(禁止)

- **達成率・進捗バー・%・スコア・連続日数(ストリーク)を出すな。**
  → 遵守率を指標にすると、隊員は確実にできる小さい計画しか立てなくなる(ADR-008)
- **できなかったこと・遅れ・未達を数えるな。赤で出すな。**
  「やり残し3件」「12日記録なし」は書かない。書いていない日は**「記録なし」とだけ静かに**(ADR-008)
- **「このペースだと○件」のような、目標との差が見える推計を出すな。**
  → 名前を変えた進捗バーになる
- **画面に説明文・注釈・チュートリアルを置くな。**説明が要る画面は形が間違っている(ADR-015)
  - 「あとから足せます」と書く代わりに、選択肢に**「あとで決める」**を入れる
  - 「担当者0だとどうなるか」を書く代わりに、その箱を**赤枠+「担当者がいません」**にする
  - 例外はお金の事故だけ(「返事が来るまでは買わないでください」/ 送信の取り消し不可 — ADR-028, 021)
- **絵文字をアイコンとして使うな。**インラインSVGで、線の太さを揃える
- **音声入力を出すな**(凍結中)
- **チャット・DM・コメントを作るな。**反応は👏だけ

## 2. 置き方

- **押せるものは最低 44×44pt。**見た目のアイコン・文字は小さくてよいが、**透明な当たり判定**で確保する。
  隣り合うタップ対象の間には視覚的な余白を置く
- **数字は右端をそろえる。**`font-variant-numeric: tabular-nums`。
  行の右側(役割/状態/操作)は**決まった幅の枠**に入れ、**要素が無い行には空の枠**を置く(ADR-021)
- **枠の入れ子を作るな。**罫線は髪の毛一本。**囲うのではなく余白で区切る**
- **色は1色だけ**(`--accent: #0f766e`)。状態はコントラストと太さで示す。赤は差戻し・破壊的操作のみ
- **決まったステップがある流れは、上にバーを置く。**初回設定 / 日報作成 / 月初プラン / 月報作成 / 経費申請。
  表示は **「1 / 3」= 手順の位置**であって、達成率ではない
- **モーダルは押した場所の近くで開く。**上部の要素から下部シートを出すな
  (振り返りの年月ピッカーは上端から落ちる。役場スマホの承認詳細は下からのボトムシート — ADR-034)
- **空でも画面が成立すること。空欄のフォームを主役に置くな。**AIが先に1案書いた状態で開く
  (今月の方向・プロジェクト目標・アクションカレンダー・月報はすべてAI下書きから始まる)
- **足すボタンは1つだけ。**2つ並べるとどちらを押すか毎回考えることになる。
  文脈(選んだ日が過去か未来か)に意味を決めさせる
- **ページ全体スクロールは、毎日開く画面(隊員スマホ)では出すな。**
  ただし絶対ではない — 項目が本質的に多い設定・管理画面は、崩れるくらいならスクロールさせる

## 3. 構造の原則

- **活動記録とプランは独立。**計画が無くても記録できる。計画は**入力を省く材料**にすぎない(ADR-043)
  - 計画の確認ステップは**計画がある日だけ出し、無ければ黙って飛ばす**。「計画がありません」も書かない
  - 記録の本線は「他に活動はあったか」の側。**記録0件でも「次へ進む」は押せる**
  - **受け入れ条件: 計画0件・定期タスク0件の隊員が、最後まで通って1日分の記録を保存できること**
- **タブの役割**: 活動=書く / 振り返り=過去 / 取組=今 / 経費 / 事例 / プロフ。
  **未来の目標タブは廃止済み**(ミッションはプロフから開く)
- **年に数回しか開かない画面を常設タブにするな。**開くたびに放置している後ろめたさを生む
  (実績・お知らせ・設定・ミッションはこの扱い — ADR-021)
- **レシートは撮るだけ。申請させるな。**撮る作業(30秒)と申請の判断は別の頭を使う(ADR-028)
- **目標も節目も任意。**未設定でもチェックインと月報が成立すること(ADR-041/043)
- **どの段にも「あとにする」を置く。**押しても決めた内容は消えない。
  「まだ決めない」は採用と**同じ強さ**で置く — 選べないと結局は強制になる
- **行き止まりを作るな。**候補に無ければ打った名前でそのまま作れる
- **入口を重複させるな。**同じ画面に同じ目的の導線を2つ以上置かない(経費の入口が4つあった失敗)
- **役場に新しい入力作業を増やすな。**読むものは隊員の行動から自動生成する(ADR-010)

## 4. 作り方(速度が最優先)

- **既存の正本を差分で直す。書き直すな。**既存の関数・CSSをそのまま流用する
  (`member-mock-v56.html` が隊員の正本。指示にもこの一文を明記する)
- **指示書は15行以内。**制約は毎回書かず、このSkillとADR番号・既存ファイル名の参照で済ませる
- **検証は既定で「JS構文チェック + headless 1パスで例外が空」だけ。**スクショは要求されたときのみ
- **独立した修正は並列に投げる。**同じファイルを2体で同時に触らせない
- **1回の指示で1つだけ変える。**まとめると時間が比例して伸びる
- 見た目の作り込みに時間を使うな。**動線が分かれば出す**
- モックの受け渡しは **Artifact を同じURLへ再公開**(ファイル添付ではJSが動かず白紙になる)
- 各画面の `memo:` に**なぜその形にしたか**を残す。特に**何を撤去したか**を書く

## 5. 迷ったら

- 「この文を消したら分からなくなるか」→ なるなら**形が間違っている**。文を直すな、形を直せ
- 「この画面を1日に何回開くか」→ 毎日ならスクロール禁止を厳しく、たまになら緩める
- 「その数字は誰のためか」→ 本人を責める数字なら出さない
- 「計画0件の人はこの導線を通れるか」→ 通れないなら設計が間違っている
