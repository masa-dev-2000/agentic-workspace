# 対策の接続表（Countermeasure Wiring）

対策1件が「次にいつ・どこで作動するか」を、作動する粒度まで降ろすための1枚。
R4で対策を書いた直後、および外部へ再発防止を説明する前に使う。

書けない欄が1つでも残る対策は、紙の上にしか存在しない。空欄は不備であって、
記入者の努力不足ではなく**対策の設計不足**を示す信号として扱う。

## なぜ必要か

再発防止が形骸化する典型は、記録・分析・対策までは書かれているのに、その対策が
**次回の実作業のどこで人やAIの目に入るのかが決まっていない**状態である。
この状態は内部レビューでは検出できない。書類はすべて揃っており、欠けているのは
文書ではなく接続だからである。

星取表は「どの業務にどの対策が要るか」を持つ。接続表はその一段下、
「その対策が実作業のどの瞬間に発火するか」を持つ。

## 接続表

| 欄 | 内容 | 空欄時の意味 |
|---|---|---|
| 事故 | 何が、いつ、どこまで出たか。事実のみ | — |
| 等級 | 軽微 / 中 / 重大（R4の判定） | 判定未了 |
| 発生系のなぜなぜ | なぜ誤ったものが**作られた**か → 構造の欠陥 | 分析未了 |
| 流出系のなぜなぜ | なぜ出る前に**止まらなかった**か → 検知の欠陥 | 分析未了 |
| 対策 | 1文 | — |
| 強度 | S1 仕組み / S2 手順 / S3 注意。S1でないなら降格理由 | 型の適用漏れ |
| **作動する工程** | 案件ワークフローのどの工程か | 対策の宛先がない |
| **作動する瞬間** | 「◯◯の直前」まで具体化 | 発火条件がない＝発火しない |
| **その時の主体** | 人 / AI / 両方 | 責任の所在が不明 |
| **何を開くか** | 具体的なファイル名・URL | 「確認する」に留まっている |
| **何と突き合わせるか** | 比較対象（一次資料・契約書・台帳） | 検証が成立しない |
| **何が残るか** | 証跡。残らないなら追跡不能 | 実施の確認手段がない |
| 検証方法 | S1は再現テスト必須 | 効果不明のまま運用 |
| 検証期日 | 日付 | 検証されない |
| 水平展開 | 同じ構造の他業務。無ければ「なし」と明記 | 未実施 |

太字の6欄が「現実との接続」であり、この表の目的はそこだけにある。

## 埋め方の判定基準

**「何を開くか」**：ファイル名かURLで答える。「関連資料」「一次資料」は不可。
開くものが特定できないなら、対策はまだ抽象度が高すぎる。

**「何と突き合わせるか」**：自社の他資料を比較対象に置いてはならない。誤りが
複数資料へ伝播していると内部整合では検出できない。一次資料とその訂正履歴を指す。

**「作動する瞬間」**：工程名だけでは足りない。人がツールを開くのは作業開始時では
なく、出す直前・消す直前である。発火点はそこに置く。

**「何が残るか」**：自己申告は証跡ではない。「引っかかった点と処置」が残る形にする。
何も引っかからなかった場合も、通した事実が残る形にする。

**強度と接続の関係**：S1（仕組み）なら「何を開くか」は自動化された検査を指し、
人の動作を書く必要はない。人の動作を書かざるを得ないならS2以下であり、
S1として記録してはならない。

**検知が成功していた場合**：異常を実際に見つけていたなら、検知は壊れていない。
そこに検知の追加を積むと、機能している工程を重くするだけで再発は止まらない。
掘るべきは検知の後段——見つけた後に選べた手が用意されていたかである。

**不可逆操作の後始末**：削除・解約の記録には**復元期限**を書く。復元窓が開いている間は
原状復帰が第一手であり、届出・再発行・代替手段はその後に検討する。期限が書かれていない
記録は、異常時に「もう戻せない」と誤認させる。

**目的と手段のずれ**：「消したい」の目的が課金の停止なら、停止で目的は満たされる。
目的に対して手段が過剰（可逆で足りるのに不可逆を選んだ）な操作は、それ自体が欠陥である。
対策は注意ではなく、工程から過剰な手段を外すことで打つ。

## 説明資料の骨子

外部（クライアント・制度側）へ再発防止を説明する場合、接続表からこの順に写す。
ツールや仕組みの名前は最後で、無くてもよい。

1. 何が起きたか（事実のみ。評価と弁明を混ぜない）
2. 直接原因ではなく**構造**として何が欠けていたか（発生系／流出系の2系統）
3. 打った対策と、その**強度**（仕組みで止まるのか、注意で止めるのか）
4. **それが次にいつ・どこで作動するか**（接続表の太字6欄）
5. 効いたかをどう確かめるか、いつ確かめるか

1〜3だけの資料は、読み手から見て「同じことが起きない理由」を含まない。
4と5が言えて初めて仕組みと呼べる。

書き方の禁止事項が2つある。

**原因の所在を否定形で書かない。**「担当者の確認漏れではありません」は、書き手には構造の
説明でも、読み手には責任の否定に読める。責任の所在を先に肯定形で言い切り（「当方の不備で
あり、責任は当方にあります」）、構造の説明はその後に、**対策が仕組み側になる理由**として
置く。同じ理由で「注意する形の措置は含めていません」も「手順と設定によって成り立つ措置に
しています」と肯定形で書く。

**読み手に関係のない自社内部の事情を書かない。**なぜその操作をしたか（契約の経緯、課金、
社内の都合）は社内記録側の情報である。外部の読み手が判断に使うのは3〜5だけであり、
内部事情はそこに寄与せず、量が増えるほど2〜5が薄まる。経緯の時系列表も、事実を1〜2文に
圧縮できるなら落とす。

`build-decision-ready-materials` が意味の所有者であり、体裁スキルはその後に呼ぶ。
外部に出す前にR1bの5点ゲートを通す。

## 運用

- 1対策 = 1枚。事故1件で対策が3つなら3枚になる
- 保存先は案件側（`criteria/data-locality.md`）。この共有ワークスペースには置かない
- 星取表の行と対策IDを共有し、二重管理しない
- 同じ構造の2件目が出たら強度を1段上げる（R4）。接続表も作り直す
- 検証期日に、証跡が実際に残っているかを見る。残っていなければ対策は作動していない
