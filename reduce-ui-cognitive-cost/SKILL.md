# Reduce UI Cognitive Cost

「見にくい」「何を押せばいいか分からない」への対処。**要素を減らす作業ではない。**

## 最初に避ける失敗

**数を減らしにいくな。** 「押せるものが32個あるから12個にする」は、数えやすいだけの代理指標で、
見やすさとは別物。要素を減らしても、強さの順番が間違っていれば見にくいままになる。

実際に起きた失敗:

> 時間帯を強調色の太字にして行の先頭に置き、合計を最大の文字にし、
> 記録も合計もレシートも同じ白いカードに入れた。要素は減ったが、
> **いちばん強い信号がいちばん重要でない要素に付いていた**ので、元より見にくくなった。

**症状は「多い」でも、原因はたいてい「強さの順番と大事さの順番が逆」。**

## 手順

### 1. 大事さの順番を、言葉で決める

その画面でユーザーが知りたい・やりたいことを、**順番付きで書き出す**。推測なら推測と明示する。

例（活動記録の画面）:
1. どの日か（間違えると事故）
2. 何をやったか（本文）＝ 主役
3. いつやったか（時間）
4. 出口（保存）

**合計・集計・設定は「探しに行くもの」**で、目に飛び込む必要はないことが多い。
誰のための情報かを問う（本人のためか、承認者のためか）。

### 2. いまの強さの順番を、実測する

推測しない。実際に測る。

- **視覚的な強さ**: 文字サイズ・太さ・色・面積・枠の有無を要素ごとに書き出す
- **押せるもの**: DOM から数える（下記スクリプト）。**数は診断材料であって目標ではない**
- **スクリーンショット**を実機・実寸で撮り、**目を細めて見る**（squint test）。
  ぼかしても残る塊が、実際に最初に目に入るもの

```js
// 押せるものと、その視覚的な強さを一覧にする
(() => {
  const sel = 'button, a[href], input:not([type=hidden]), textarea, select, [role=button], [tabindex]:not([tabindex="-1"])';
  const vis = e => { const r = e.getBoundingClientRect();
    return r.width > 0 && r.height > 0 && getComputedStyle(e).visibility !== 'hidden'; };
  const items = [...document.querySelectorAll(sel)].filter(vis);
  const w = e => { const s = getComputedStyle(e);
    return { t: (e.getAttribute('aria-label') || e.textContent || '').trim().slice(0, 20),
             size: s.fontSize, weight: s.fontWeight, color: s.color }; };
  return JSON.stringify({ count: items.length, items: items.map(w) }, null, 1);
})()
```

### 3. ズレを名指しする

1 と 2 を並べ、**順位が入れ替わっている箇所**を具体的に挙げる。
「なんとなく見にくい」で終わらせない。「◯◯が△位なのに視覚的には1位」と書く。

### 4. 原則に沿って直す

- **色は操作にだけ使う。** 情報に強調色を使うと、押せるものが分からなくなる。
  強調色が画面に3か所以上あったら、たいてい間違っている
- **文字は3段階まで。** 主役 / 補助 / 極小。5段階あると階層が読めなくなる
- **余白でまとめる。** 関係あるものは近づけ、無いものは離す。
  全部が同じ間隔だと、どこで区切れているか読めない（近接の原則）
- **枠を減らす。** カードの枠は階層を作らない。**枠が同じなら全部同じ重さに見える**。
  区切り線と余白だけで構造を作れないか試す
- **右端の桁を揃える。** 状態・操作は決まった幅の枠に入れ、**無い行には空の枠を置く**。
  ボタンの有無で右端がずれると目が横に泳ぐ
- **反復を守る。** 同じ意味のものは同じ形で繰り返す。
  **意味が違うものに同じ形を与えない**（カードが4枚あって中身が全部違う種類なら、
  目は「同じものの繰り返し」と読んで区別をやめる）
- **リストの行の高さを揃える。** 可変長のテキストをそのまま流すと、長さで行の高さが
  バラバラになり、区切りの位置が読めなくなる。**1行または最大2行で切る**（`text-overflow`,
  `-webkit-line-clamp`）。全文は行を開いたときに見せる
- **終わったことは出さない。** 「提出済み」「確認待ち」など**行動が要らないもの**が枠を
  取っていたら消す。出すのは行動が要るときだけ

### 見た目が古く見えるときに効くもの

「ダサい」と言われたら、たいていこの5つのどれか。

- **枠線をやめ、面の明度差で階層を作る。** 全部に 1px の線を引くと、要素の重さが揃って
  しまい階層が消える（地 #f0f4f9 / 面 #fff のような2段で足りる）
- **角丸を大きく。** 10〜14px は古い。パネル 24〜28px、ボタンは pill（完全角丸）
- **影を使わない。** 高さは色の差で表す
- **余白を増やす。** 左右 20→24px、行 13→16px、グループ間 22→30px、行間 1.5→1.65
- **ラベルの大文字＋字間空けをやめる。** 小さめの通常字にする

Material 3 では **FAB が円ではなく角丸の四角**（16px）、ナビの選択状態は**薄い面のピル**。
細部が古いと全体が古く見える。

### 5. 案を2〜3個出す。違いは「視線の落とし所」だけにする

**同じデータ・同じ原則で、目の行き先だけを変える。**
色や余白のルールを案ごとに変えると、何を比べているのか分からなくなる。

よく効く軸:
- **内容ファースト**: 主役の情報を最大・最濃に。属性は下に小さく添える
- **軸を通す**: 左に時間軸・カテゴリ軸の柱を置き、流れを形で見せる。空きが余白として見える
- **紙1枚**: 枠を全部やめ、区切り線と余白と文字の階層だけにする

### 6. 実機で確認する

**スクリーンショットは実寸で撮る。** 縮小して並べると、どの案も同じに見える。
狭い画面（390×844 等）と広い画面の両方で見る。

- 横のはみ出しが無いか
- 情報が増えたとき（行が4件・8件）に破綻しないか
- 空のときに間延びしないか

## 報告のしかた

- **自分の案の誤りを先に認める。** 指摘が当たっているなら、そう書いてから直す
- ズレを具体的に名指しする（「時間帯を緑の太字にしたのが誤り」）
- 案ごとに **どこに目を落とさせたいか**を1文で書く
- **推測は推測と書く。** 実ユーザーに聞いていないなら明示する

## 進め方（このユーザーの好み）

- **常に3案以上出す。** 1案だけ出して「これでどうですか」と聞かない。
  比べる相手がないと判断できない
- **案を比べるときは変数を1つに保つ。** 見た目を作り直すなら構造は据え置く。
  構造を比べるなら見た目を揃える。両方変えると何を比べているのか分からなくなる
- **勝手に順番を変えない。** 「1画面ずつ、まずログイン直後の画面から」と言われたら、
  途中で入力画面に移らない。診断した画面がたまたま別だった、は理由にならない
- **決定はモックで見せてから。** 実装に入る前に、動くモックで形を確認する
- **モックは実際に動かす。** 静止画ではなく、押せる・回せる・切り替わるところまで作る
- **2択に見えたら疑う。** 「AとBのどちらを取るか」と書いたら、たいてい前提を1つ見落として
  いる。**両方の利点を取る第3の形**がないか探してから聞く

## サンプルデータの書き方

**利用者を子供扱いしない。** 「ラフなメモ」を表現するのに、ひらがなに崩すのは誤り。
実際の業務メモは**省略して短く書く**もの。

```
✗ 空き家2けんまわった　1けんは前向き     ← 小学生の作文に見える
○ 空き家2軒 訪問 1軒前向き 登記の確認要   ← 実際のメモ
```

## やらないこと

- 要素数だけを根拠に「改善した」と言わない
- 機能を削って認知コストを下げたことにしない（**別の問題**）
- 画面に説明文を足して解決しない。**説明が要る形は形が間違っている**
- **同じ入力に2つの手段を並べない**（スロットがあるのにプリセットのチップも出す、等）
- **プリセット・既定値を「今」から作らない。** 実行時刻に依存する既定値は、朝と夕方で
  まったく違う値になる。**時刻に左右されない1つの規則**にする
