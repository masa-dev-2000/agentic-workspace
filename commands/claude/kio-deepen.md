登録済みのGitHubイシューを深掘りし、仕様を確定させる。

引数:
- issue番号（カンマ区切りで複数指定可）
- 引数なし: 未着手（🔴）のIssueを全件対象にする

例:
  /kio-deepen           ← 未着手のIssue全件
  /kio-deepen 173
  /kio-deepen 173, 174, 175

## 概要
`/kio-issues` で簡易登録されたIssueに対して、コードベースを調査し、
仕様決定に必要な不足情報をユーザーに質問して、仕様を確定させる。
実装方針はここでは決めない。仕様（何を作るか）を決めるのがこのステップ。

## 重要ルール
- **実装方針を勝手に書かない**。仕様（ユーザーから見た振る舞い）を確定させるのが目的
- **不足情報は必ずユーザーに質問する**（AskUserQuestion）。勝手に推測して埋めない
- **複数件指定された場合も1件ずつ順番に処理する**。1件の仕様が確定してから次へ進む

## 手順（1件ずつ実行）

### Step 0: 対象Issueの特定（引数なしの場合）

引数が指定されていない場合、/kio-status と同じロジックで未着手（🔴）のIssueを特定する。
- オープンIssueを取得
- PR・ブランチとの紐付けがないIssueを抽出
- 対象一覧をユーザーに提示し、どのIssueから深掘りするか確認する

### Step 1: Issue内容の取得

```bash
gh issue view <N> --json number,title,body,labels -q '"#\(.number): \(.title)\n\(.body)"'
```

### Step 2: コードベース調査（内部作業、結果はユーザーに直接見せない）

Issueの内容に関連するファイルを grep → Read の順で調査する:
- 現在どう動いているか（現状の仕様）
- Issueの要望を実現するために決めるべきこと（仕様上の未決定事項）

### Step 3: ユーザーに質問する

調査結果をもとに、仕様を確定させるために必要な質問をAskUserQuestionで行う。

質問の形式:
```
## #<N>: <タイトル>

### 現状
<今どうなっているかを簡潔に説明>

### 確認したいこと
1. <仕様上の未決定事項A>？
2. <仕様上の未決定事項B>？
3. ...
```

質問のポイント:
- ユーザーの意図・期待する振る舞いを確認する
- 「AとBどちらにしますか？」のように選択肢を提示すると答えやすい
- エッジケースの扱い（0件の場合、上限超過の場合など）を確認する
- 技術的な内部実装の詳細は聞かない（それは /kio-imple で決める）

### Step 4: ユーザーの回答をもとにIssueを更新

ユーザーの回答を受けて、確定した仕様をIssueに追記する。

```bash
gh issue edit <N> --body "<元の本文>\n\n---\n\n## 確定仕様\n<ユーザーの回答を反映した仕様>"
```

追記する内容はユーザーの言葉をベースに、以下の形式で整理:
```
## 確定仕様
- <仕様1: ユーザーから見た振る舞いの記述>
- <仕様2>
- ...
```

### Step 5: 完了報告と次のIssueへ

```
✅ #<N> の仕様を確定しました
```

複数件の場合は次のIssueのStep 1に進む。
全件完了後にサマリーを表示:
```
✅ 仕様確定（N件）
| # | タイトル | 状態 |
|---|---------|------|
| #173 | xxx | 仕様確定 |
| #174 | yyy | 仕様確定 |

実装: /kio-imple 173, 174
```

## トークン節約ルール
- grep → Read の順序を守る
- 同一ファイルの再Read禁止
- 必要最小限のファイルのみ調査
